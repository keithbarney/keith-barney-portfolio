Atlas Component Docs

Role
Design Systems Lead
Organization
Experian Consumer Services, North America
Platforms
Web, iOS, and Android

Context

I regularly designed Atlas components and handed them to development, but the team needed a consistent, repeatable way to deliver both the component and its documentation. Creating that documentation manually was time-consuming and prone to inconsistencies.

Existing documentation plugins did not match the team’s structure or visual approach, so the workflow was a strong candidate for automation based on information already present in the component.

Atlas Component Docs accepts a component or component instance, analyzes its associated information, and generates structured documentation directly on the Figma page.

Approach

Generated documentation

Users can turn sections on or off for each run: Overview, Anatomy, Variants & Properties, Breakpoints, Content Guidelines, and Accessibility. When supported, the output can include related components, sub-components, properties, variant values, do and don’t guidance, keyboard behavior, focus visibility, and name, role, and value guidance.

Shared implementation language

The documentation also captures broader patterns such as spacing, layout, forms, and feedback, turning decisions into a reusable reference. Keeping design intent near the component gives engineers richer context for behavior, content, accessibility, and responsive implementation across Atlas’s target platforms.

Configurable output

Users can change the documentation background color when a component state—such as a light-gray skeleton loading treatment—would otherwise lose clarity against the canvas. Generated instances can be arranged vertically or horizontally: wide components may read better in a vertical stack, while narrow or vertical components can be easier to compare side by side.

Adoption

Library contribution

Designers can create a library branch, add a proposed component, generate its documentation, and submit the contribution for review. The plugin lowers friction without removing the need for design judgment.

Published for the team

I published the plugin for the broader design team. Other designers use it and report that it saves time, while the generated structure helps contributions meet documentation expectations more consistently.

Richer handoff

By carrying usage, states, properties, variants, and accessibility guidance with the component, the workflow gives engineers more useful implementation context and reduces repetitive layout work.

Outcomes

Faster documentation

Designers can generate a structured starting point instead of rebuilding the same documentation layout by hand, reducing repetitive work during contribution.

Consistent outputs

Shared sections and visual conventions make contributed documentation easier for designers and engineers to scan, compare, and use across Atlas.

Lower contribution friction

The workflow strengthens design-to-development handoff and makes it more likely that a proposed component includes useful guidance before review.

Now

Component maturity sets the ceiling

Documentation quality reflects the component’s structure. A component with few properties or incomplete metadata produces a sparse result; a well-constructed component can produce richer guidance. That transparency helps designers see where a component needs more structure before handoff.

Automation still needs judgment

The plugin exposes what the component already communicates, but it does not replace designer judgment or the work of making the component complete, intentional, and ready to contribute.

In active use

Atlas Component Docs is part of the ongoing library-contribution workflow: a practical way to turn component structure into documentation that designers and engineers can use together.
